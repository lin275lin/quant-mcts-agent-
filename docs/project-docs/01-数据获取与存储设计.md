# 数据获取与存储设计

> 对应模块：`core/data/`、`app/agents/data/`
> 状态：设计稿（待评审）　最后更新：2026-11-23

## 1. 要解决的问题

一句话：**查询股票数据时，先看我们自己存了什么，最后才去外部库抓。**

外部接口（akshare、tushare 等）有三个毛病：慢、限频、字段会变。如果每次查询都打接口，系统会被网络卡死，回测也复现不了。所以数据获取按三级来：内存缓存 → 本地数据库 → 外部库兜底，并且单独记录一份"我们到底有哪些数据"的清单。

## 2. 三级读取策略

```
                  ┌──────────────────────────────┐
   请求 ────────▶ │ L1  Redis 热缓存              │ 命中 → 直接返回（毫秒级）
  (symbol,区间)   └──────────┬───────────────────┘
                             │ 未命中
                  ┌──────────▼───────────────────┐
                  │ 查询数据目录（catalog）        │ 覆盖满足 → 读 DB → 回填 Redis
                  │ 判断已存区间是否够用           │
                  └──────────┬───────────────────┘
                             │ 有缺口
                  ┌──────────▼───────────────────┐
                  │ L2  本地数据库（明细）          │ 读缺口部分
                  └──────────┬───────────────────┘
                             │ 仍缺
                  ┌──────────▼───────────────────┐
                  │ L3  外部数据源（最后兜底）      │ 只抓缺口 → 校验 → 落库 → 更新目录
                  └──────────────────────────────┘
```

三条纪律：

1. **数据库是唯一权威**（single source of truth）。Redis 只是缓存，可以随时清空重建；外部库只负责补洞，不负责每次查询。
2. **catalog 决定"要不要出门"**。没有 catalog 就只能靠试，试一次打一次接口。
3. **L3 只抓缺口**，不整段重抓。已有 2020–2024，要 2023–2025，只抓 2024-01 之后。

### 2.1 取数单位：单股五年

单只股票用五年数据做 MCTS 逼近，据此确定几条约定：

- **默认窗口**：`start = 最近交易日 − 5 年`，约 1215 个交易日；实际起止日与行数以 catalog 为准。
- **次新股按实际长度**：上市不足五年就取上市首日至今，不补零、不向前填充，`data_asset.row_count` 记录真实行数。
- **整段读取、整段缓存**：搜索期间数据常驻内存（约 100KB/股），MCTS 的 rollout 内部**不允许查库或查 Redis**，否则 IO 会拖垮热循环。
- **计算量参考**：6 个因子 × 1215 行，一次向量化回测约 1–3ms；1000 次 rollout 约 1–3 秒。瓶颈在 rollout 次数，不在数据长度。
- **五年不能整体用来搜权重**：训练段 3 年给 MCTS，验证段 1 年定超参，测试段 1 年只报结果。全样本搜索 + 同段回测即过拟合。
- **质量要求**：五年必然跨除权、停牌、ST、退市，因此必须存不复权价 + 复权因子 + 停牌/涨跌停标记；否则收益率计算失真。

### 2.2 因子清单与所需字段（20 个）

目标因子池 20 个，分七类。**行情只能支撑前四类和规模、技术类；估值与质量类必须额外落地两类数据。**

| 类别 | 因子（共 20 个） | 所需原始字段 | 频率 |
| --- | --- | --- | --- |
| 动量（4） | 20/60/120 日收益、5 日反转 | 后复权 close | 日 |
| 波动（3） | 20 日、60 日波动率、下行波动率 | 后复权 close | 日 |
| 流动性（3） | 20 日换手率均值、成交额均值、Amihud 非流动性 | volume、amount、turnover_rate、circ_mv | 日 |
| 估值（3） | PE-TTM、PB、PS-TTM | pe_ttm、pb、ps_ttm | 日 |
| 质量（4） | ROE、营收同比、净利润同比、资产负债率 | 净利润、营业收入、净资产、总资产、总负债 | 季 |
| 规模（1） | 流通市值对数 | circ_mv | 日 |
| 技术（2） | RSI(14)、20 日量价相关性 | close、volume | 日 |

**因此数据层要落三类资产**（`data_asset.asset_type`）：

| asset_type | 内容 | 来源 | 备注 |
| --- | --- | --- | --- |
| `bars` | 日线 OHLCV、成交额、换手率、复权因子、停牌/涨跌停 | akshare | 主表 |
| `valuation` | PE/PB/PS/股息率、总市值、流通市值 | akshare 乐咕接口（按 symbol 拉全历史） | 日频 |
| `financial` | 净利润、营收、净资产、总资产、总负债 | akshare 财务摘要 | 季频，按报告期 |

两个必须注意的口径问题：

1. **财务数据要按公告日对齐**（point-in-time）。akshare 的财务摘要只给报告期，没有公告日，若直接按报告期使用，等于提前知道未来。现阶段用“报告期 + 90 天”近似，**必须在论文里写明这是近似处理**，并在因子层留一个 `announce_date` 字段便于以后替换。
2. **估值与规模用原始价，动量/波动用后复权价**。同一张因子矩阵里两种价格口径并存，计算时要显式区分，不要图省事全用后复权。

## 3. 数据目录（catalog）：回答"我们有哪些数据"

这是整套设计里最容易被忽略、但最关键的一张表。它记录每个数据资产的存在与质量，不存明细。

### 表 `data_asset`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `asset_id` | TEXT PK | `daily:600519.SH:20200101-20241231` 这种可读 ID |
| `symbol` | TEXT | 标准代码，带交易所后缀 |
| `freq` | TEXT | `1d` / `1m`（先只支持 1d） |
| `field_set` | TEXT | 字段集版本，如 `ohlcv_v1`；加字段就换版本 |
| `start_date` | DATE | 实际起始日 |
| `end_date` | DATE | 实际截止日 |
| `row_count` | INT | 行数 |
| `missing_days` | INT | 按交易日历算出的缺失天数 |
| `source` | TEXT | `akshare` / `tushare` / `import` |
| `source_version` | TEXT | 接口或库的版本号，便于追责 |
| `checksum` | TEXT | 数据内容 sha256（排序后序列化），用于判断是否被改过 |
| `snapshot_id` | TEXT | 所属快照版本（见第 6 节） |
| `status` | TEXT | `ok` / `partial` / `quarantined` |
| `created_at` / `updated_at` | TIMESTAMP | |

索引：`(symbol, freq, start_date, end_date)`。查询"600519 有没有 2023 年数据"就是一次索引命中。

### 表 `fetch_log`

每次真正打外部接口都记一条：`symbol / 请求区间 / 命中层（L1/L2/L3）/ 耗时 ms / 返回行数 / 结果状态 / 错误信息 / 时间`。作用有两个：一是排查"为什么这次特别慢"，二是给论文的"系统测试"章节提供真实数据。

## 4. Redis 的用法

只放三类东西，全部带 TTL，绝不作为唯一副本。

| 键 | 内容 | TTL | 说明 |
| --- | --- | --- | --- |
| `bars:{symbol}:{start}:{end}` | 序列化后的 DataFrame（msgpack/parquet bytes） | 1h | 查询结果缓存，最热的一层 |
| `cov:{symbol}:{freq}` | 覆盖区间列表 + 更新时间 | 10min | 避免每次查询都打 DB 的 catalog |
| `latest:{symbol}` | 最新一根日线 | 到下一交易日 15:30 | 盘中反复查同一只股票的场景 |
| `lock:fetch:{symbol}` | 抓取互斥锁（SETNX） | 60s | 防并发重复抓同一只股票 |

**降级**：Redis 连不上时，整条链路自动跳过 L1 直接走 DB，只记一条告警日志。缓存永远不是必需品。

## 5. 数据库表（明细）

### 表 `bar_daily`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `symbol` | TEXT | |
| `trade_date` | DATE | |
| `open/high/low/close` | NUMERIC | **不复权原始价** |
| `volume` | BIGINT | 股 |
| `amount` | NUMERIC | 元 |
| `turnover_rate` | NUMERIC | 换手率 % |
| `adj_factor` | NUMERIC | 复权因子，回测时再算，不预先改价 |
| `is_suspended` | BOOL | 停牌 |
| `limit_up` / `limit_down` | BOOL | 涨跌停 |
| `source` | TEXT | 便于同一天多源比对 |

主键 `(symbol, trade_date)`，写入用 UPSERT，天然幂等。

> 不复权 + 复权因子分列存的原因：前复权价格会随新数据变化，历史快照就不可复现；存原始价 + 因子，任何时点都能重算出当时的复权序列。

### 表 `valuation_daily`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `symbol` / `trade_date` | TEXT / DATE | 主键 |
| `pe_ttm` / `pb` / `ps_ttm` | DECIMAL(18,4) | 估值，缺失时留 NULL，不要填 0 |
| `dv_ttm` | DECIMAL(12,6) | 股息率 |
| `total_mv` / `circ_mv` | DECIMAL(20,2) | 总市值 / 流通市值（元） |

主键 `(symbol, trade_date)`。估值倍数按数据源返回值保存，亏损导致的负 PE 也保留。因子层对有效且非零的倍数取倒数，缺失或无法计算时留空。

### 表 `financial_report`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `symbol` / `report_date` | TEXT / DATE | 主键；`report_date` 为报告期（如 2025-09-30） |
| `announce_date` | DATE | 公告日；**字段存在但当前为近似值**（报告期 + 90 天） |
| `net_profit` / `revenue` | DECIMAL(20,2) | 净利润、营业收入 |
| `equity` / `total_asset` / `total_liab` | DECIMAL(20,2) | 净资产、总资产、总负债 |
| `roe` | DECIMAL(10,6) | 净资产收益率，若源已给则直接用 |

主键 `(symbol, report_date)`。因子层按 `announce_date` 做 as-of join，杜绝未来函数。

## 6. 快照（parquet）

DB 是"可查询的权威"，parquet 是"冻结的版本"。只在明确要"冻结一次实验"时导出：

```
storage/raw/daily/2026-11-23/
├─ bars.parquet           明细导出（长表）
├─ adj_factor.parquet
└─ manifest.json          数据源、区间、股票池、行数、缺失统计、checksum、对应 snapshot_id
```

manifest 里的 `snapshot_id` 同时写回 `data_asset`，做到"快照 ↔ 目录"双向可查。论文里的实验章节必须写明用了哪个 snapshot_id。

## 7. 写入路径（L3 抓回来之后）

```
外部接口 → 原始响应落盘（storage/raw/_raw/，便于排错）
        → 字段清洗与类型转换
        → 校验 6 条规则（见下）
           ├─ 通过 → UPSERT 进 bar_daily
           │        → 更新 data_asset（区间取并集、重算 row_count 与 checksum）
           │        → 回填 Redis
           └─ 不通过 → 写 quarantine 表（结构同 bar_daily，多一列 error_reason）
                      + 告警，data_asset.status 置 quarantined，不污染正式表
```

校验规则：

1. 日期不重复、不越界；
2. `close > 0`，`high >= max(open, close)`，`low <= min(open, close)`；
3. 单日涨跌幅不超过板块限制（主板 10%、创业板/科创板 20%、ST 5%）；
4. 停牌日成交量为 0 且价格不变；
5. 与已有数据重叠部分逐行比对，冲突时保留旧数据并记录差异；
6. 按交易日历算缺失率，超过 1% 标 `partial`。

## 8. 对外接口（Agent 只认这三个函数）

```python
ensure_coverage(symbols, start, end) -> list[Gap]   # 查 catalog，算缺口
get_daily(symbol, start, end) -> DataFrame          # 三级读取，返回数据
fetch_if_missing(gaps) -> FetchReport               # 只给缺口走向 L3
```

`app/agents/data/workflow.py` 的四步（parse → resolve → ensure → export）里，第 ③ 步 `ensure` 内部就是"`ensure_coverage` → `fetch_if_missing` → `get_daily`"。

## 9. 选型

| 组件 | 选定 | 理由 |
| --- | --- | --- |
| 缓存 | **Redis 7** | 热缓存 + 抓取互斥锁，本地 Docker 一条命令起 |
| 数据库 | **MySQL 8.0（InnoDB）** | 千万行级单表足够；本机已装、团队/简历熟悉；答辩常见组合，评委也熟 |
| 备选库 | SQLite | 兜底：零部署，单机单用户够用；并发写弱 |
| 备选库 | DuckDB | 分析层：直接查 parquet 很快，适合实验统计，可后加 |
| 外部源 | **akshare** 主 | 免费、A 股日线全 |
| 外部源 | tushare 作交叉校验 | 字段规范，但需积分 |

规模估算：5000 只股票 × 2500 交易日 ≈ 1250 万行，MySQL 单表完全撑得住，不需要时序库。

### 9.1 MySQL 落地注意（与 PostgreSQL 的差异）

用 SQLAlchemy 2.x + Alembic 管理表结构，绝大多数方言差异被屏蔽，但下面几条要提前记住：

1. **UPSERT 写法不同**：MySQL 用 `INSERT ... ON DUPLICATE KEY UPDATE`，没有 `ON CONFLICT`。用 SQLAlchemy 的 `mysql_insert(...).on_duplicate_key_update(...)`，别手写 SQL 字符串。
2. **DECIMAL 必须写精度**：价格 `DECIMAL(18,4)`、复权因子 `DECIMAL(18,6)`、成交额 `DECIMAL(20,2)`。不写精度默认 `DECIMAL(10,0)`，小数会被截掉。
3. **主键与分区**：如果以后按 `trade_date` 做分区，MySQL 要求分区键包含在主键里。当前主键 `(symbol, trade_date)` 已满足，可以直接按年分区；不分区也完全够用。
4. **时间字段用 DATETIME，不要用 TIMESTAMP**：TIMESTAMP 会按时区隐式转换、范围只到 2038 年。统一存 UTC 的 DATETIME，展示层再转本地时区。
5. **字符集统一 utf8mb4**：库、表、连接三处都要（`charset=utf8mb4`），否则 `symbol` 里的特殊字符或备注会报错。
6. **批量写入分批**：1000～5000 行一批做 `on_duplicate_key_update`，单条 INSERT 会在千万行时慢到不可用。
7. **索引别重复**：主键 `(symbol, trade_date)` 已能覆盖"某只股票某区间"的查询；如果要做"某日全市场"统计，再加一个 `(trade_date)` 索引即可，不要给 `symbol` 单独建索引。

外部源用适配器隔离，只暴露：

```python
class BarSource(Protocol):
    name: str
    def fetch_daily(self, symbol: str, start: date, end: date) -> DataFrame: ...
```

换库只改一个实现类，`core/data/` 其余代码不动。

## 10. 一致性与运维

- **对账任务**：每天跑一次 `catalog 声明的行数/区间` vs `bar_daily 实际行数/区间`，不一致就修 catalog 并告警。
- **重建**：Redis 全清不影响正确性；DB 可由 parquet 快照 + fetch_log 重建。
- **并发**：抓取前拿 `lock:fetch:{symbol}`，拿不到就排队或直接返回已有数据。

## 11. 风险

| 风险 | 应对 |
| --- | --- |
| 三层不一致（catalog 说有一万行，实际九千） | 每日对账 + checksum |
| 外部接口改字段、限频 | 适配器 + 重试退避 + 原始响应留档 |
| Redis 或 DB 挂掉 | Redis 挂了跳过缓存；DB 挂了只读 parquet 快照 |
| 过度设计 | 先只实现 L2 + L3（SQLite + akshare），Redis 用接口占位，跑通后再接 |
